# KIMS — лендинг франшизы

Next.js 16 (App Router) + Tailwind v4 + next-intl. Четыре языка: `uk` (основной), `en`, `es`, `ru`.

## Запуск

```bash
npm install
cp .env.example .env.local   # заполнить ADMIN_PASSWORD
npm run dev                  # http://localhost:3003
```

## Структура

- `src/app/[locale]/` — сам лендинг, страница собирается из секций в `src/components/site/`
- `src/app/admin/` — админка (`/admin`, пароль из `ADMIN_PASSWORD`)
- `content/{uk,en,es,ru}.json` — **эталонные тексты сайта** из репозитория.
  На сервере рабочая копия живёт в `CONTENT_DIR` (см. ниже) и правится админкой
- `src/lib/paths.ts` — где лежат данные админки: `CONTENT_DIR`, `UPLOADS_DIR`,
  `DATA_DIR`. Если каталог пуст, он заполняется эталоном из репозитория
- `public/img/` — оптимизированные фото (WebP), `design-assets/` — исходники из
  Figma, в сборку не попадают

## Деплой на Hostinger (Business, Node.js Web App)

Приложение собирается на сервере из подключённого GitHub-репозитория: пуш в
основную ветку — редеплой. Node 20.9+ (требование Next.js 16).

Команды приложения:

```
установка сборки: npm ci && npm run build
запуск:           npm run start
```

`npm run start` слушает порт из переменной `PORT`, которую выдаёт хостинг —
поэтому порт нигде не прописан жёстко. Локально сайт поднимается на 3003
командой `npm run dev`.

Минимум переменных:

```
ADMIN_PASSWORD=<пароль для первого входа>
LEADS_SAVE_LOCAL=1
```

Данные админки по умолчанию складываются в `$HOME/kims-data` — то есть выше
папки приложения, поэтому редеплой их не трогает. Если хостинг кладёт домашний
каталог в другое место, пути задаются явно:

```
CONTENT_DIR=<путь>/content
UPLOADS_DIR=<путь>/uploads
DATA_DIR=<путь>/leads
```

Рабочая копия контента достраивается эталоном из репозитория: всё, что
добавлено в код после первого запуска, — новое поле, новая секция, изменённая
структура блока — доезжает на работающий сайт автоматически. Правки заказчика
при этом главнее, перезаписываются только отсутствующие ключи.

Фактические пути и права на запись видно в админке, раздел «Настройки и доступ»
→ «Где хранятся данные». Если каталог недоступен, сайт всё равно поднимется на
текстах из репозитория — сборка из-за этого не падает, — но правки сохранить
не получится, и админка это покажет.

`ADMIN_PASSWORD` нужен только для первого входа: в админке, раздел
«Настройки и доступ», задаётся свой пароль — он хранится хешем в `CONTENT_DIR`
и дальше имеет приоритет над переменной. Адрес сайта и разрешение на
индексацию задаются там же, переменная `SITE_URL` остаётся запасным вариантом.

Каталоги создавать руками не нужно: при первом обращении приложение создаст их
и скопирует туда тексты из репозитория. Дальше репозиторий и рабочий контент
живут независимо — деплой меняет только код.

Загруженные файлы отдаются маршрутом `/media/*` (`src/app/media/[...path]`),
потому что лежат вне `public/`.

## Переезд со старого сайта

На `kims-franchise.com` до этого работал одностраничник на WordPress. В его
карте сайта было ровно две страницы: главная и `/privacy-policy/`. Главная
попадает на языковую версию сама, для политики добавлен постоянный редирект
в `next.config.ts`. Якоря старого меню (`#about`, `#firstline`, `#eco` и
прочие) на сервер не передаются, поэтому такие ссылки просто открывают
главную — отдельных правил не требуют.

На старом сайте лежали два PDF в `/wp-content/uploads/2023/10/` — их можно
переиспользовать как презентацию для новой формы.

## Технический домен

На Business-тарифе Hostinger можно поднять до пяти Node-приложений, поэтому
основной и технический сайт — это два приложения из одного репозитория,
но с разных веток и с разными переменными.

| | Основной | Технический |
|---|---|---|
| ветка | `main` | `staging` |
| `SITE_URL` | боевой домен | технический поддомен |
| `SITE_NOINDEX` | не задавать | `1` |
| каталоги данных | свои | **отдельные**, не общие с боевыми |

Индексация выключена по умолчанию: свежий сайт не попадёт в поиск, пока в
админке не поставят галочку. На техническом домене её лучше закрыть жёстко —
`SITE_NOINDEX=1` отдаёт `robots.txt` с полным запретом обхода и добавляет
`noindex` в мета-теги — технический домен не попадёт в поиск и не будет
конкурировать с основным. `robots.txt` и `sitemap.xml` читают окружение на
каждом запросе, поэтому не зависят от того, при каких переменных шла сборка.

Порядок работы: правки уезжают в `staging` → проверяются на техническом
домене → сливаются в `main` → уезжают на боевой.

Каталоги данных обязательно разные: иначе правки, сделанные в админке
технического сайта, тут же уйдут на боевой.

## SEO

Что правится в админке:

- **SEO и мета-теги** — `title` и `description` на каждый язык, отдельные
  заголовок и описание для соцсетей (если пустые — берутся обычные),
  загрузка Open-Graph-картинки (любое фото приводится к 1200×630)
- **Alt-тексты картинок** — альты ко всем фото сайта, на четыре языка
- **Картинки сайта** — замена любого фото с автосжатием в WebP

Что работает само: `sitemap.xml` с четырьмя языковыми версиями и hreflang,
`robots.txt`, canonical и hreflang в `<head>`, Open Graph и Twitter-карточки.

## Слайдер кейса и картинки

Фото слайдера лежат в реестре `media.json` внутри `CONTENT_DIR` (общий для всех языков),
подписи — в локализованных `content/{locale}.json` в `case.slides`, по ключу
слайда. Добавление, порядок и удаление — в админке, раздел «Слайдер кейса»:
загруженный файл автоматически сжимается в WebP (до 2400px, качество 82) и
кладётся в `UPLOADS_DIR`. При удалении слайда чистятся и файл, и подписи.

Подпись при загрузке копируется во все четыре языка, чтобы сайт не показывал
пустоту; в списке слайдов непереведённые подписи помечены.

## Презентация

PDF, который партнёр получает после заявки. Загружается в админке, раздел
«Презентация», лежит в `UPLOADS_DIR/presentation.pdf` — имя фиксированное,
чтобы ссылка не менялась при перезаливке. Пока файл не загружен, кнопки на
сайте просто ведут на форму; после загрузки кнопка на скачивание появляется
на экране «дякуємо» сразу после отправки заявки.

Лимит на загрузку через серверные действия поднят до 40 МБ в `next.config.ts`
(по умолчанию 1 МБ — не хватало ни на фото с телефона, ни на PDF).

## История правок

Перед каждым сохранением из админки складывается полный снимок текстов и
реестра медиа в `CONTENT_DIR/.history` (хранятся последние 30). Раздел
«История изменений» показывает список точек и откатывает сайт к любой из них
в один клик. Сам откат тоже пишется в историю, поэтому обратим.

Публикация при этом остаётся мгновенной: заказчик сохраняет — изменение сразу
на сайте, а страховка от неудачной правки — откат, а не режим черновика.

## Cookie и аналитика

Баннер не декоративный: пока посетитель не нажал «Прийняти», счётчики не
подключаются. Google Analytics включается переменной `NEXT_PUBLIC_GA_ID` и
грузится только после согласия. Выбор хранится в localStorage.

Страница политики — `/[locale]/privacy`, текст правится в админке в разделе
«Политика конфиденциальности», переносы строк сохраняются. Страница закрыта
от индексации.

## Заявки

`POST /api/lead` — валидация, затем рассылка по всем настроенным каналам.
Ошибка канала не влияет на ответ посетителю: заявка к этому моменту уже
записана, а сбой уходит в лог. Что настроено — видно в админке на `/admin/leads`.

**Telegram.** Создать бота у `@BotFather`, добавить его в группу и дать право
писать. `TELEGRAM_CHAT_ID` — идентификатор группы, у групп он отрицательный
(например `-1001234567890`); узнать можно, отправив сообщение в группу и открыв
`https://api.telegram.org/bot<токен>/getUpdates`.

```
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
```

**Почта.** SMTP того ящика, с которого уходят письма. Для почты Hostinger это
`smtp.hostinger.com`, порт 465.

```
SMTP_HOST=smtp.hostinger.com
SMTP_PORT=465
SMTP_USER=<ящик>
SMTP_PASS=<пароль ящика>
LEADS_EMAIL_TO=egorova@kims.com.ua
```

В админке, раздел «Заявки», есть кнопка «Отправить тестовую заявку»: она шлёт
пробное сообщение по настроенным каналам и показывает результат по каждому —
включая текст ошибки от Telegram или почтового сервера. Проверять настройку
удобнее так, а не заполняя форму на сайте.

Дополнительно: `LEADS_WEBHOOK_URL` — любой вебхук с JSON (CRM, Make),
`LEADS_SAVE_LOCAL=1` — дублировать в `DATA_DIR/leads.jsonl`, чтобы видеть заявки
в админке и выгружать CSV.
